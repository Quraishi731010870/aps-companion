SCOPE
Responsibility boundary

Who does what?

APS Settlement Engine

  • Builds and validates settlement batches
  • Generates stable financial message IDs
  • Signs requests with APS private signing key
  • Encrypts for ACSS using ACSS public certificate
  • Verifies ACSS responses before state changes
  • Reconciles every submitted record

ACSS Settlement Platform

  • Authenticates transport and decrypts requests
  • Verifies APS signature before processing
  • Validates and processes each record
  • Returns a result for every message ID
  • Signs responses and encrypts them for APS
  • Persists idempotency and audit evidence
Trust boundary: HTTP success alone is never proof that a financial entry was accepted or settled.
PRINCIPLES
Non-negotiable behavior

Core integration principles

One batch

One request represents one settlement batch with a records array.

Stable record ID

Shared batch ID

Complete response

Exactly one outcome for every submitted message ID.

Explicit direction

Layered security

JWS + JWE + HTTPS/mTLS; each control has a distinct purpose.

ENVELOPE
On-the-wire request

Illustrative request envelope

{
  "schemaVersion": "1.0",
  "messageType": "SETTLEMENT_REQUEST",
  "sender": "APS",
  "recipient": "ACSS",
  "signingKeyId": "APS-SIGN-KEY-2026-01",
  "encryptionKeyId": "ACSS-ENC-KEY-2026-01",
  "payloadFormat": "JWS-IN-JWE",
  "encryptedPayload": "<JWE compact token>"
}

Critical interpretation

  • The business JSON is inside the signed JWS.
  • The signed JWS is encrypted inside JWE.
  • Outer metadata is not trusted until matched to protected headers.
  • The final profile must choose wrapper JSON or raw JWE.
  • Content type and serialization require ACSS approval.
Never send the example business payload as plaintext in production.

RESPONSE
Per-record accountability

Every submitted ID needs one outcome

Required echoed fields

  • financialMessageId
  • settlementType and amount
  • currency
  • settlementBatchId and batchDate

Outcome fields

  • status: ACP or RJC
  • rejectReason: required for RJC
  • Stable machine-readable reason code
  • Human-readable description
Open semantic decision: ACP must mean exactly one lifecycle state—received, validated, accepted for settlement, or fully settled.
APS decrypts and verifies the ACSS signature before storing results or changing any settlement status.

▣

JWE or CMS

Authenticates both network endpoints and protects the transport connection.

SECURITY CONTROLS
Production baseline

Controls required before go-live

  • Approved algorithms, serialization and canonical byte representation
  • HSM or approved key-management service for private keys
  • Certificate chain, validity, usage and revocation checks
  • Trust-store governance and expiry monitoring
  • Planned and emergency key rollover procedures
  • Unique request ID, timestamps, expiry window and replay cache
  • Network allowlisting where appropriate
  • Least privilege and separated UAT/production secrets
  • Access-controlled audit evidence and monitoring
  • Incident response and key-compromise playbook
Never log private keys, credentials, plaintext financial payloads or decrypted sensitive fields in general application logs.
IDEMPOTENCY
Safe retries

A timeout must not create a second posting

SubmitStable financialMessageId
TimeoutOutcome is unknown—not failed
Query / retryReuse same IDs and payload
DeduplicateACSS returns prior result
ReconcileExactly one trusted outcome

Same ID + same payload

Return the previously stored result without applying the entry again.

Same ID + different payload

Reject as a conflict and escalate for investigation.

ACSS should persist request digests and results. A batch ID must not be reused for materially different content.

RECONCILIATION
Completeness controls

Submitted set must equal returned set

Request IDs = Response IDs

  • Exactly one result for each submitted ID
  • No missing IDs
  • No duplicate results
  • No unexpected IDs
  • All echoed financial fields match
  • Totals agree by currency and direction

Quarantine conditions

  • Signature verification failure
  • Unknown or expired signing key
  • Batch reference mismatch
  • Altered amount, currency or direction
  • Partial, duplicate or foreign results
  • Replay outside the permitted window

ACCEPTANCE
Definition of done

Joint acceptance criteria

  • APS submits a protected multi-record batch
  • ACSS decrypts and verifies the APS signature
  • ACSS returns a signed and encrypted response
  • APS decrypts and verifies before status updates
  • Every ID receives exactly one ACP or RJC result
  • Every RJC includes an approved reason code
  • Retries cannot create duplicate posting
  • Tampering, invalid certificates and replay fail closed
Mandatory gate: no message is processed or trusted until its digital signature has been successfully verified.
